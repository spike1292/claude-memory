# The eval gate: soft, opt-in, and fail-closed

**Date:** 2026-09-04 · **Status:** shipped · **Issue:** [#87](https://github.com/spike1292/claude-memory/issues/87)

## Question

`--run` printed `recall@k` and MRR and always exited 0, so a regression was reported and then
ignored. Two loops are queued behind #87 — a self-improving retrieval loop (#88) and automatic
promotion to `permanent/` (#96) — and both remove today's accidental safety, which is that a human
reads every note before it counts. What accept/reject rule should the gate use, and when does it
refuse?

## Why a gate at all

Microsoft's SkillOpt ran the ablation we would otherwise have run ourselves: same model, same
candidate edits, five rounds, only the validation gate toggled.

| | Night 0 → Night 5 | Delta |
| --- | --- | --- |
| no gate | 0.554 → 0.026 | **−52.8 pts** |
| with gate | 0.570 → 0.570 | 0.0 |

Ungated, the optimizer distilled a plausible rule from real trajectories and accuracy collapsed
monotonically. The gated twin rejected every one of those edits. Single seed (42, their own open
issue #108 says so), so the sign and the order of magnitude are what transfer, not the third digit.
Read on 2026-09-04 from <https://github.com/microsoft/SkillOpt> (MIT), `docs/sleep/RESULTS.md` for
the table and `configs/features/soft_gate.yaml` for the stall they document. Cited by URL rather
than by an internal note, because this repo is public and the reading should not have to be redone.

## Decision

**Soft, with a named threshold.** `--min-rank1 <percent>` compares `recall@1` against a floor the
caller states. It is not a strict-improvement gate against an incumbent.

A hard gate requires a candidate to *strictly beat* the incumbent, and SkillOpt's own
`configs/features/soft_gate.yaml` documents where that stalls: a small selection split plus a
continuous partial-credit score means candidates improve per-item scores without ever flipping a
discrete outcome, so the gate rejects everything forever. That is exactly this situation. The real-
vault sets hold 28 EN and 15 NL cases — one case is 3.6 points — and `recall@k` is continuous.
Choosing the soft form up front is cheaper than discovering the stall.

**Threshold: none by default; the caller names one.** No number is written into the code, because
the only honest floor is one measured against a specific case set and this repo has already shipped
five artefacts' worth of retrieval figures whose provenance nobody could reconstruct. A floor
belongs in the command that invokes the gate, beside the case set it was measured on.

**Opt-in.** Without `--min-rank1`, `--run` is a report and behaves exactly as it did. Every existing
caller wants the report.

## Fail-closed, and its one boundary

Under a floor, a case that could not be scored at all **blocks the run**. Unscorable is separate
from "scored zero": no results returned, a non-finite score, or a gold/owner note that is not in the
vault. `metrics()` counts them apart from misses and the report names each one, because this repo's
characteristic failure is the silent fallback and a tally is the quiet form of it.

The boundary: unscorable blocks only when a floor was asked for. The `churn` band in
`goldCoverage()` has always warned about a pruned gold note and scored past it, and refusing that
unprompted would break every plain `--run`. Asking for a floor is asking for an accept/reject
decision, and that decision is the one that must fail closed.

**A pairwise case is the exception, and fails the run with or without a floor.** It is an assertion,
not a metric: a case naming an `owner` says another note rightfully owns the question, and the
runner checks that the owner *outranks* the named note. The owner must be **found**, not merely
ahead — a question matching nothing satisfies "the named note did not win" and would otherwise pass
precisely when retrieval is broken. No existing case set has an `owner` field, so this changes
nothing for any current caller.

## Held-out sets

A tuning set may be fitted to; a held-out set may not, and the distinction is mechanical rather than
remembered: `--kind held-out` resolves its own filename (`…-heldout.jsonl`) and every report and
JSON envelope echoes the kind. A number whose set kind is unknown is not printable.

The reported kind is read off the **resolved path**, not off the flag. `--cases` names a file
outright, so `--kind held-out --cases <a tuning set>` would otherwise print a tuning number under a
held-out label — the mislabelling the kind exists to prevent, reached by the override path instead
of by the typo `defaultCasesPath` already throws on.

`--freeze` writes a sha256 sidecar and `--run` refuses a set that no longer matches it. The sets
stay machine-local because they carry vault content, so "this was not edited to fit the result"
cannot be shown by publishing the questions — the hash is quotable where the questions are not.

## What this does not do

It does not build the loop (#88), it does not author questions, and no retrieval change may ship on
the numbers this produces in the same PR. This is instrumentation.
